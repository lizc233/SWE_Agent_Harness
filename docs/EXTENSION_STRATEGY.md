# MCP 与多 Agent 扩展策略

## 当前决定

0.1.0 暂不加入 MCP 或多 Agent 运行时。原因不是做不了，而是当前唯一版本化评测只证明单 Agent Harness 闭环；没有证据表明增加分布式复杂度能提高成功率。

## 何时加入 MCP

满足任一条件再实现：

- 真实任务需要访问当前工具池没有的外部系统；
- 至少两个外部服务需要统一工具发现与命名空间；
- 可用评测证明 MCP 工具相对本地适配器减少维护成本。

实现准入：异步生命周期、工具命名空间、超时、权限继承、Schema 冲突、服务断开与重连都必须有测试。

## 何时加入多 Agent

满足以下全部条件再实现：

- 单 Agent 在多个固定任务上因上下文或并行瓶颈稳定失败；
- 子任务可以明确隔离输入、工作目录和产出；
- 有基线可比较成功率、成本和延迟；
- 合并冲突、取消、所有权和失败归并语义已设计。

## 为什么这反而更适合面试

工程判断不是“功能越多越好”，而是用评测决定复杂度。面试时可以说明：先完成单 Agent 可审计闭环，再用真实失败数据决定是否引入 MCP 或多 Agent，避免为了关键词增加无法验证的系统复杂度。
