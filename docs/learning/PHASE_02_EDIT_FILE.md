# Milestone 2：`edit_file` 要点

## 为什么不能只做 `text.replace()`

如果旧文本出现了两次，模型可能只打算改一个位置。盲目替换会污染代码；如果旧文本一次都没找到，继续报告成功会让后续测试建立在假修改上。

因此工具要求：

- `old_text` 非空；
- 默认必须恰好命中 1 次；
- 多次替换必须显式提供 `expected_replacements`；
- 计数不匹配时文件保持不变。

## 为什么使用原子写入

直接覆盖原文件时，进程在写到一半崩溃可能留下半个文件。实现先在同一目录写临时文件、刷新并 `fsync`，然后用 `os.replace` 一次性替换目标文件。这样失败发生在替换前时，原文件仍然存在。

这不是完整的并发控制：两个 Agent 仍可能先后读取同一旧内容。后续需要加入文件哈希或版本条件，防止覆盖用户的新修改。

## 当前安全边界

`edit_file` 已经是写能力，但当前注册表仍未接入 allow/deny/ask 权限层。它适合本地开发演示，不应直接对不可信仓库或无人值守流程开放。

## 面试表达

“我没有把编辑实现成无条件字符串替换，而是要求旧文本精确命中预期次数；失败时不改文件。写入采用同目录临时文件加 `os.replace`，降低进程中断造成半写文件的风险。下一步会在工具执行前加入分级权限和用户审批。”
